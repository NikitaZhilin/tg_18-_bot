# Аналитика, выводы и предложения по доработке

## Краткий вывод

Текущее ТЗ стало заметно сильнее после сверки с двумя прошлыми Telegram-проектами.

Главный вывод: этот бот нужно строить не как набор callback-кнопок вокруг одной таблицы `cards`, а как маленькое stateful-приложение: сессии, turns, persisted timers, контент-валидация, heartbeat/status, retry polling и строгие safety-гейты.

После анализа нового файла с заданиями добавился еще один вывод: контент нужно нормализовать до матрицы `level + category + intensity`. Особенно для уровней 3 и 4 нельзя просто "добавить пожестче"; нужна градация `light / medium / hard`, ручной review и отключение опасных карточек по умолчанию.

### Приватный Telegram-бот

Полезные паттерны:

- SQLite для состояния;
- отдельный `DATA_DIR`;
- `/status` и `/reset`;
- `chat_key = chat_id:thread_id`;
- разбиение длинных сообщений перед отправкой в Telegram;
- хранение контекста отдельно от Telegram handlers.

Что применено к текущему ТЗ:

- добавлен `chat_key`;
- добавлен `DRY_RUN`;
- усилена конфигурация `.env`;
- добавлен `/status`;
- добавлено требование не логировать приватный текст;
- добавлен `DATA_DIR`;
- добавлена эксплуатационная часть.

### `tg_bot_inkubator`

Полезные паттерны:

- разделение `handlers`, `keyboards`, `services`, `repositories`, `migrations`;
- бизнес-логика тестируется без Telegram-объектов;
- кнопочные сценарии надежнее свободного AI-чата для MVP;
- контент хранится отдельно от кода;
- есть migration-подход;

- на Windows нужен `tzdata`;

- специальные сценарии нельзя прятать внутри обычного потока;
- баги FSM нужно фиксировать регрессионными тестами.

Что применено к текущему ТЗ:

## Главные доработки текущего ТЗ

### 1. Сессии и turns вместо `is_turn` в `users`

Исходная идея `users.is_turn` слишком хрупкая. Ход - это свойство конкретной игровой сессии, а не пользователя.

Нужно:

- `sessions.current_player_id`;
- `sessions.active_turn_id`;
- `turns.status`;
- `turns.card_id`;
- `turns.selected_intensity`;
- `used_cards(session_id, card_id)`.

Это даст нормальное восстановление после перезапуска и защитит от двойных callback-нажатий.

### 2. Отдельные FSM-ветки для специальных сценариев

Опыт инкубатора показал реальный UX-баг: специальный режим был спрятан внутри обычного чек-листа, и пользователь попадал не туда.

Для текущего бота это особенно важно:

- безопасный пропуск не должен вести в штраф;
- уровень 4 не должен быть просто обычной кнопкой уровня;
- стоп-слово не должно проходить через обычное завершение хода;
- "Русская рулетка" должна уважать safety-фильтры.

### 3. Реквизит лучше хранить нормализованно

Одна строка `requires_item` не подходит, потому что карточка может требовать несколько предметов.

Нужно:

- `items`;
- `card_required_items`;
- `session_items`.

`session_items` важнее `inventory_json`, потому что по нему проще фильтровать и тестировать выборку.

### 4. Таймеры должны быть persisted

Если таймер хранить только в памяти FSM, он потеряется при перезапуске.

Нужно:

- `timers`;
- `deadline_at`;
- `status`;
- `timer_runner`;
- защита от повторного запуска одного таймера.

### 5. Safety-гейты должны быть частью данных

Уровень 4 и рискованные карточки нельзя контролировать только текстами.

Нужно в карточках:

- `safety_level`;
- `risk_tags`;
- `requires_both_opt_in`;
- `is_enabled`.

Нужно в сессии:

- `allow_level_4`;
- `safety_preset`;
- подтверждения обоих игроков.

### 6. Контент должен проходить импорт и валидацию

`Задания.docx` уже можно распарсить, но импорт не должен молча загружать все подряд.

Нужен pipeline:

1. DOCX -> промежуточный CSV.
2. Парсинг уровня, таймера, реквизита.
3. Автотеги риска.
4. Отчет о проблемных карточках.
5. Ручное подтверждение.
6. Seed в SQLite.

### 7. Runtime нужно сразу проектировать как реальный бот

Из инкубатора видно, что бот может быть "логически исправен", но не работать из-за:

- умершего процесса;
- stale pid;
- отсутствия `.venv`;
- отсутствия `tzdata` на Windows;
- Telegram network timeout;
- блокировки Telegram маршрутом;
- отсутствия proxy.

Поэтому в ТЗ добавлены:

- `start-bot.ps1`;
- `stop-bot.ps1`;
- `status-bot.ps1`;
- `smoke_start.py`;
- retry polling;
- `TELEGRAM_PROXY_URL`;
- heartbeat.

### 8. Контент уровней 3-4 требует отдельной матрицы интенсивности

Текущий файл содержит только `13-24` по каждому уровню. Для уровней 1-2 нужно восстановить недостающие `1-12`. Для уровней 3-4 целевое состояние после твоего уточнения:

- уровень 3: 48 заданий, по 16 `light`, `medium`, `hard`;
- уровень 4: 48 заданий, по 16 `light`, `medium`, `hard`;
- hard-карточки не равны "опасные"; hard означает максимальную интенсивность внутри согласованных и технически безопасных рамок.

Карточки с дыхательным контролем, травмами, отсутствием быстрого освобождения, состоянием опьянения или медицинским риском нужно не усиливать, а отключать и выносить в ручную проверку.

### 9. Админка нужна уже в первом рабочем релизе

CSV/XLSX остается лучшим массовым способом наполнения, но для постоянной эксплуатации неудобно каждый раз редактировать файл и перезапускать импорт.

Нужна Telegram-админка:

- добавить карточку;
- сохранить черновик;
- отправить на проверку;
- одобрить;
- отключить;
- отредактировать;
- посмотреть историю изменений;
- импортировать файл;
- экспортировать текущую базу.

Чтобы админка не сломала безопасность, рабочая выдача должна брать только:

```text
is_enabled = 1
review_status = approved
```

Все действия пишутся в `admin_actions`, а прошлые версии карточек - в `card_versions`.

## Улучшенная продуктовая логика

### Старт сессии

Лучший поток:

```text
/start
-> Проверка доступа
-> Продолжить активную сессию / Начать новую
-> Выбор реквизита
-> Подтверждение базового согласия
-> Ход игрока
```

### Уровень 4

Поток:

```text
Уровень 4
-> Объяснение, что это отдельный рискованный режим
-> Подтверждение игрока 1
-> Подтверждение игрока 2
-> Только после этого уровень доступен
```

Если бот работает в одном общем чате, подтверждение можно принимать от двух разных разрешенных `user_id`.

### Замена карточки

Лучший поток:

```text
[Заменить карточку]
-> Карточка завершена как skipped
-> Отменяется ее таймер
-> С теми же фильтрами сразу выдается другая карточка
-> Ход остается у того же игрока
```

Штраф:

```text
[Игровой штраф]
-> Доступен только если включен режим штрафов
-> Выдает только карточки category=penalty, safety_level=normal
```

### Таймер

Таймер должен быть связан с `turn_id`, а не просто с текстом карточки. Это позволит:

- не запускать один таймер дважды;
- отменять таймер по `/stopword`;
- восстановить таймер после рестарта;
- показать таймер в `/status`.

## Риски после повторной проверки

| Риск | Оценка | Что изменить в ТЗ |
|---|---:|---|
| Рискованные карточки уровня 4 попадут в обычную рулетку | Высокий | Уровень 4 только после opt-in, рискованные cards disabled по умолчанию |
| Повторное нажатие выдаст 2 карточки | Высокий | `turns` + транзакция + idempotent callbacks |
| Стоп-слово сработает как обычный reset | Высокий | Отдельный `SafetyService.stop_session()` |
| Таймер потеряется после рестарта | Средний | Таблица `timers` + runner |
| Реквизит с несколькими items не отфильтруется | Средний | `card_required_items` и `session_items` |
| Бот умер, но пользователь этого не видит | Средний | heartbeat + `/status` + status script |
| Telegram заблокирован сетью | Средний | retry polling + `TELEGRAM_PROXY_URL` |
| Контент из DOCX импортируется с ошибками | Средний | Import report + validation |

## Что теперь стоит сделать перед кодингом

1. Создать `content/cards.csv` из `Задания.docx`.
2. Сразу отключить или пометить карточки с высоким риском.
3. Утвердить, будет ли игра идти в общем чате или в личных чатах двух игроков.
4. Утвердить два Telegram User ID.
5. Утвердить правило уровня 4: включен только вручную и только после двух подтверждений.
6. Утвердить, нужен ли штраф в MVP. Мой вывод: не нужен в MVP, лучше сделать позже.
7. Утвердить SQL-схему v3.

## Рекомендуемый следующий инженерный шаг

Не начинать с Telegram handlers. Сначала сделать ядро:

```text
ContentImporter -> CardPicker -> GameService -> SafetyService -> TimerService
```

И покрыть это unit-тестами. После этого Telegram-слой будет тонким и менее хрупким.

Практический порядок:

1. `app/storage/database.py` + schema/migrations.
2. `app/services/content_importer.py`.
3. `app/services/card_picker.py`.
4. `app/services/game_service.py`.
5. `app/services/safety_service.py`.
6. `tests/test_card_picker.py`.
7. `tests/test_game_service.py`.
8. Только потом aiogram handlers/keyboards.

## Результат повторной проработки v3

Реализация теперь закрывает основные эксплуатационные проблемы, найденные по скриншотам:

- вместо поиска одной строкой появился каталог `раздел -> тип -> 10 карточек на страницу`;
- карточки можно открыть, изменить, одобрить, отключить, архивировать и удалить;
- реквизит вынесен в отдельный каталог с добавлением, изменением, архивом и удалением;
- XLSX стал русским, разделен по уровням и пригоден для обратного импорта;
- общая рулетка учитывает выбранные для сессии уровни;
- замена карточки не передает ход и не повторяет уже показанную карточку;
- интенсивный контент отделен в появляющийся после пароля раздел `Экстрим`;
- тексты очищены от внутренних названий и непоясненных английских терминов;
- стартовые CSV больше не перезаписывают административные правки после перезапуска.

Оставшиеся разумные улучшения после стабилизации: расширенный редактор risk-тегов и полей поз
прямо в Telegram, резервное копирование SQLite по расписанию и отдельный журнал результатов
массового импорта. Эти задачи не блокируют текущий приватный релиз.
