# Техническое задание v3 на Telegram-бота для интимной игры

## 1. Цель и границы продукта

Нужно разработать приватного Telegram-бота для пошаговой игры для двух взрослых партнеров.

Бот выдает случайные карточки с контентом разных типов:

- `question` - вопрос;
- `task` - задание;
- `pose` - поза с описанием или медиа;
- `desire` - желание-купон;
- `penalty` - легкое штрафное задание, если этот режим включен.

Выдача карточек зависит от:

- выбранного уровня;
- категории;
- интенсивности;
- доступного реквизита;
- настроек безопасности текущей сессии;
- истории уже выпавших карточек.

MVP должен быть детерминированным кнопочным ботом, а не свободным AI-чатом. Основная ценность - стабильная игровая механика, приватность, понятные состояния и безопасный выход из любого сценария.

## 2. Опыт из существующих Telegram-ботов

ТЗ доработано с учетом проверенных решений из двух прошлых направлений:

- старый приватный Telegram-бот с whitelist, SQLite-контекстом, `DRY_RUN`, `/status`, `/reset`, разделением контекста по `chat_id:thread_id`;
- `tg_bot_inkubator`, где уже реализованы FSM-сценарии, сервисный слой, репозитории, миграции, heartbeat/status, retry polling, proxy-настройка, тесты и контент вне кода.

Ключевые решения, которые нужно перенести:

- бизнес-логику держать в `services`, Telegram-слой - только в `handlers`;
- все callback-сценарии делать state-aware и idempotent;
- специальные сценарии выводить отдельной веткой до входа в обычный поток, а не прятать внутри него;
- хранить контент отдельно от кода;
- иметь `DRY_RUN`/smoke-режим для проверки без реального Telegram API;
- добавить `/status` для владельцев и технические heartbeat-записи;
- не логировать приватный текст карточек и пользовательские интимные ответы;
- учитывать сетевые сбои Telegram через retry и опциональный `TELEGRAM_PROXY_URL`;
- на Windows закладывать `.venv`, `tzdata` и запуск через штатные scripts.

## 3. Приватность и доступ

### 3.1. Белый список

Бот должен обслуживать только два заранее заданных Telegram User ID.

Дополнительно поддерживается приватный режим, когда два игрока играют с одного Telegram-аккаунта:

```text
SINGLE_ACCOUNT_TWO_PLAYERS=true
ALLOWED_TELEGRAM_USER_IDS=111
PLAYER_1_NAME=Игрок 1
PLAYER_2_NAME=Игрок 2
```

В этом режиме один Telegram User ID проходит whitelist, а очередность ведется виртуальными слотами
`player_1` и `player_2`.

Конфигурация:

```text
BOT_TOKEN=...
ALLOWED_TELEGRAM_USER_IDS=111,222
PLAYER_1_NAME=...
PLAYER_2_NAME=...
ADMIN_TELEGRAM_USER_IDS=111,222
ALLOW_UNLISTED_USERS=false
SINGLE_ACCOUNT_TWO_PLAYERS=false
```

`ALLOW_UNLISTED_USERS=true` допустим только для локальной отладки.

Если пишет неразрешенный пользователь:

- по умолчанию ответить: "Доступ закрыт";
- не создавать сессию;
- не писать текст его сообщений в лог.

### 3.2. Чат и thread

Бот должен хранить `chat_key`:

```text
telegram_chat_id:telegram_thread_id
```

Это позволит безопасно разделять:

- личный чат;
- общий чат пары;
- topic/thread внутри Telegram-группы, если он появится позже.

В MVP можно использовать один общий чат пары, но модель БД должна поддерживать `chat_key`.

### 3.3. Логи

Запрещено писать в debug/info-логи:

- полный текст карточек;
- ответы игроков на вопросы;
- приватные заметки;
- токены и ID медиа.

В логах допустимы:

- `card_id`;
- `session_id`;
- `user_id`;
- callback-код;
- технический статус.

## 4. Безопасность игры

### 4.1. Стоп-слово

Команда `/stopword` и кнопка `[Стоп-слово]` должны быть доступны на каждом игровом экране.

При стоп-слове бот обязан:

- мгновенно остановить активную сессию;
- отменить активную карточку;
- отменить активный таймер;
- записать событие в `safety_events`;
- показать нейтральное сообщение;
- вернуть меню в безопасное состояние.

Текст:

```text
Игра остановлена. Сделайте паузу и обсудите, все ли в порядке.
```

Стоп-слово не должно запускать штрафы, случайные карточки или продолжение хода.

### 4.2. Замена карточки

Нужно разделить два действия:

- `[Заменить карточку]` - безопасно закрывает текущую карточку и сразу выдает другую;
- `[Игровой штраф]` - опциональный playful-режим, если оба игрока включили его в настройках сессии.

Замена сохраняет текущего игрока, уровень, категорию, интенсивность и режим рулетки. Замененная
карточка записывается как использованная и не должна повториться в этой сессии. Ее таймер
отменяется, а желание-купон не сохраняется. Штраф не должен автоматически срабатывать при замене.

### 4.3. Уровень 4

Уровень 4 не должен быть доступен по умолчанию.

Для включения уровня 4 требуется:

- отдельный переключатель в настройках сессии;
- подтверждение обоих игроков;
- возможность отключить его в любой момент;
- исключение опасных карточек через `risk_tags` и `is_enabled`.

Карточки с повышенным риском должны иметь:

```text
safety_level = hard
requires_both_opt_in = true
intensity = hard
```

Рискованные темы вроде дыхательных ограничений, травм, воска, жесткой фиксации, принуждения, алкоголя как условия сцены и унижения не должны попадать в MVP без отдельной ручной модерации контента.

Запрещенные для автоимпорта теги:

- `minor_or_age_ambiguous`;
- `non_consent`;
- `coercion`;
- `blackmail`;
- `incapacitated_partner`;
- `breath_control`;
- `choking`;
- `suffocation`;
- `injury`;
- `blood`;
- `cutting`;
- `needles`;
- `weapon`;
- `intoxication`;
- `drug_use`;
- `no_quick_release_restraint`;
- `neck_restraint`;
- `circulation_risk`;
- `non_consent_roleplay_without_opt_in`;
- `medical_risk`;
- `unsafe_wax`;
- `fire`;
- `electric_shock`;
- `public_nonconsenting_people`;
- `recording_without_consent`;
- `sharing_private_media`;
- `non_human_participant`;
- `self_harm`;
- `unbounded_humiliation`;
- `irreversible_marks`.

Если такая карточка есть в исходнике, импортер должен ставить `review_status = disabled` и `is_enabled = 0`.

### 4.4. Подтверждение сессии

Перед стартом игры бот должен показать короткое подтверждение:

```text
Игра только для взрослых партнеров по взаимному согласию.
Стоп-слово доступно в любой момент.
```

Кнопки:

- `[Подтверждаю]`;
- `[В меню]`.

Для уровня 4 подтверждение должно быть отдельным.

В режиме `SINGLE_ACCOUNT_TWO_PLAYERS=true` базовое подтверждение, уровень 4 и hard-интенсивность
подтверждаются одним whitelist-пользователем, потому что оба виртуальных игрока находятся в одном
Telegram-аккаунте.

## 5. Игровой процесс

### 5.1. Старт

`/start`:

1. Проверить whitelist.
2. Определить игрока.
3. Показать главное меню.
4. Если активной сессии нет, предложить начать новую.
5. Если активная сессия есть, предложить продолжить или сбросить.

### 5.2. Выбор реквизита

Перед стартом сессии бот спрашивает: "Что сегодня используем?"

Интерфейс: inline-кнопки с циклическим состоянием:

```text
выключен -> редко -> иногда -> часто -> выключен
```

Начальный список:

- `ice` - лед;
- `oil` - масло;
- `rope` - веревка;
- `blindfold` - повязка;
- `vibrator` - вибратор;
- `headphones` - наушники;
- `candle` - специальная свеча;
- `clamps` - зажимы;
- `food` - еда.
- `lubricant` - лубрикант;
- `gloves` - одноразовые перчатки;
- `towel` - полотенце;
- `pillow` - подушка;
- `chair` - устойчивый стул;
- `sterile_urethral_kit` - специальный стерильный набор, доступный только для совместимых закрытых карточек.

Выбранный реквизит и его частота хранятся в `session_items`. Для предмета задаются совместимые
уровни, категории и короткая инструкция. При выдаче карточки бот случайно добавляет только
подходящий предмет с учетом заданной частоты. Специальный реквизит с `randomizable = 0`
используется только карточками, где он указан как обязательный.

### 5.3. Очередность ходов

Ход относится к игровой сессии, а не к пользователю глобально.

Текущее состояние:

- `sessions.current_player_id`;
- `sessions.current_player_slot`;
- `sessions.active_turn_id`;
- `turns.status`.

После завершения или безопасного пропуска ход переходит ко второму игроку.

Если оба игрока играют с одного Telegram-аккаунта, `current_player_id` остается тем же, а
`current_player_slot` переключается между `player_1` и `player_2`. Бот должен показывать имя
следующего виртуального игрока.

### 5.4. Основной ход

Поток:

1. Главное меню хода.
2. Выбор уровня.
3. Выбор интенсивности, если выбран уровень 3 или 4.
4. Выбор категории.
5. Выдача случайной подходящей карточки.
6. Выполнение, пропуск, таймер или стоп-слово.
7. Завершение turn.
8. Передача хода.

На каждом игровом экране есть `[В меню]`. Переход в меню не завершает `turn` и не очищает
`sessions.active_turn_id`. В главном меню при наличии незавершенного хода показывается
`[Продолжить текущую карточку]`. До завершения или пропуска этой карточки выдача новой запрещена.

Заголовок карточки формируется ботом и не показывает внутренний ID:

```text
Разогрев · Задание №21
```

Номер считается по порядку внутри сочетания `уровень + категория`.

Техническое правило: выдача карточки и запись `used_cards` должны происходить в одной транзакции.

Если выбрана интенсивность `hard`, бот должен показать дополнительное подтверждение и записать согласие обоих игроков как `session_consents.consent_type = hard_intensity`. Это не заменяет opt-in уровня 4: уровень 4 и жесткая интенсивность проверяются отдельно.

### 5.5. Русская рулетка

Режим случайного выбора выбирает карточку без ручного выбора уровня и категории.

Дополнительно должна быть рулетка выбранного уровня: пользователь выбирает уровень, нажимает
`[Рулетка уровня]`, и бот случайно выбирает карточку любого типа
`question/task/pose/desire` в рамках этого уровня и разрешенных safety-фильтров.

Фильтры все равно обязательны:

- whitelist;
- активная сессия;
- выбранный реквизит;
- `is_enabled = 1`;
- `review_status = approved`;
- `safety_level` разрешен настройками сессии;
- `intensity` не выше `sessions.max_intensity`;
- уровень 4 разрешен только после opt-in;
- карточка не использована в текущей сессии.

Если уровень 4 не разрешен, рулетка не должна выбирать его карточки.

### 5.6. Пустая выборка

Если карточек не найдено, бот не должен зависать.

Сообщение:

```text
Подходящих карточек не осталось или они не подходят под выбранный реквизит.
```

Кнопки:

- `[Выбрать другой уровень]`;
- `[Выбрать другую категорию]`;
- `[Изменить реквизит]`;
- `[Сбросить использованные карточки]`;
- `[Главное меню]`.

## 6. Таймеры

Карточки с временем должны иметь `timer_seconds`.

При выдаче такой карточки бот показывает кнопку `[Запустить таймер]`.

Когда время истекло, бот отправляет сообщение в Telegram:

```text
Время вышло.
```

Таймер должен храниться в БД:

- `turn_id`;
- `started_by`;
- `duration_seconds`;
- `deadline_at`;
- `status`.

Если бот перезапущен:

- активные таймеры должны восстановиться, если deadline еще в будущем;
- просроченные таймеры должны быть отмечены как `expired` и отправить одно уведомление, если это возможно.

На MVP допустимо сделать runner с периодической проверкой раз в 5-10 секунд.

## 7. Контент

### 7.1. Основной формат

Карточки хранить вне кода.

Рекомендуемый формат для редактирования:

```text
content/cards.csv
```

Допустимо держать исходник в `content/cards.xlsx`, но импорт в БД должен идти через валидируемый CSV/seed-скрипт.

Колонки:

```text
external_id
level
category
intensity
title
text
required_items
timer_seconds
media_file
media_id
pose_family
pose_difficulty
space_required
body_load
avoid_if_tags
source_note
safety_level
risk_tags
requires_both_opt_in
requires_safeword_check
aftercare_required
is_enabled
review_status
notes
```

### 7.2. Импорт из текущего DOCX

Файл `Задания.docx` нужно преобразовать в таблицу карточек.

Автоматически извлекаются:

- уровень из заголовка;
- категория `task`;
- текст;
- реквизит из `[Реквизит: ...]`;
- таймер из `[Таймер: ...]`;
- risk-теги по словарю.

После импорта нужен отчет:

- сколько карточек импортировано;
- сколько отключено из-за риска;
- сколько требует ручной проверки;
- какие карточки не удалось распарсить.

### 7.3. Валидация контента

Перед загрузкой контента seed-скрипт должен проверять:

- `level` от 1 до 4;
- `category` из разрешенного списка;
- непустой `text`;
- корректные `required_items`;
- `timer_seconds` больше 0 или пусто;
- все карточки уровня 4 имеют `requires_both_opt_in = 1`;
- карточки с опасными `risk_tags` отключены по умолчанию.
- для уровней 3-4 заполнен `intensity`;
- для `intensity = hard` заполнены `requires_both_opt_in`, `requires_safeword_check`, `aftercare_required`;
- для `category = pose` заполнены `pose_family`, `pose_difficulty`, `space_required`, `body_load`;
- `review_status = approved` разрешен только после ручной проверки.

### 7.4. Целевые объемы заданий

Текущий прикрепленный файл содержит продолжение `13-24`, то есть по 12 заданий на каждый уровень.

Целевое состояние:

| Уровень | Цель по заданиям `task` | Интенсивность |
|---:|---:|---|
| 1 | 24 | без дробления |
| 2 | 24 | без дробления |
| 3 | 48 | `light` 16, `medium` 16, `hard` 16 |
| 4 | 48 | `light` 16, `medium` 16, `hard` 16 |

Нужно восстановить недостающие `1-12` для уровней 1-2, а уровни 3-4 расширить до 48 карточек каждый. Подробный план расширения лежит в `docs/content-expansion-plan.md`.

### 7.5. Админка контента

Админку нужно заложить сразу, а не откладывать на неопределенное будущее.

Доступ к админке:

- только `ADMIN_TELEGRAM_USER_IDS`;
- пользователь должен одновременно проходить whitelist;
- все изменения пишутся в `admin_actions`;
- перед публикацией карточки показывается preview.

Команда:

```text
/admin
```

Главное меню админки:

- `[Добавить карточку]`;
- `[Каталог карточек]`;
- `[Каталог реквизита]`;
- `[Импорт XLSX]`;
- `[Экспорт XLSX]`;
- `[Экстрим: доступ закрыт/открыт]`;
- `[Главное меню]`.

UX-правила:

- у служебных админских сообщений должны быть возвраты `[В админку]` и `[Главное меню]`;
- каталог карточек открывается через выбор раздела, затем типа карточки;
- списки карточек и реквизита выводятся по 10 пунктов со стрелками страниц;
- в строке карточки показываются ID, тип, интенсивность и состояние;
- поиск должен работать по `external_id`, названию и тексту карточки;
- у карточки должны быть действия просмотра, редактирования, одобрения, отключения, архивирования и удаления;
- у реквизита должны быть действия добавления, редактирования, архивирования, восстановления и удаления;
- любое действие публикации требует финального подтверждения;
- новые и импортированные карточки по умолчанию не должны попадать в игру без review.

#### Добавление карточки

Поток:

1. Выбрать тип: `question`, `task`, `pose`, `desire`, `penalty`.
2. Выбрать уровень.
3. Для уровней 3-4 выбрать `intensity`.
4. Ввести название.
5. Ввести текст.
6. Выбрать реквизит.
7. Указать таймер или "без таймера".
8. Указать risk-tags.
9. Для `pose` заполнить `pose_family`, `pose_difficulty`, `space_required`, `body_load`.
10. Прикрепить медиа или оставить без медиа.
11. Получить preview.
12. Сохранить как `draft`, отправить в `needs_review` или сразу `approved`, если админ подтверждает.

Черновик нужно сохранять после каждого значимого шага в `cards` со статусом `draft`, чтобы его можно было продолжить после перезапуска бота или случайного выхода из wizard.

Безопасные дефолты новой карточки:

```text
review_status = draft
is_enabled = 0
requires_both_opt_in = 0
requires_safeword_check = 0
aftercare_required = 0
```

Если выбран `level = 4` или `intensity = hard`, дефолты меняются:

```text
requires_both_opt_in = 1
requires_safeword_check = 1
aftercare_required = 1
is_enabled = 0
```

В рабочую выдачу попадают только карточки:

```text
is_enabled = 1
review_status = approved
```

#### Редактирование

Админ должен уметь:

- искать карточки по ID, уровню, категории, интенсивности и тегам;
- редактировать текст и поля;
- отключать карточку без удаления;
- возвращать карточку в `needs_review`;
- смотреть историю изменений;
- откатываться к прошлой версии.

Каждое изменение сохраняет snapshot в `card_versions`.

#### Массовый импорт

Админ может отправить CSV/XLSX файлом в Telegram или положить файл в `content/`.

Перед реальным импортом нужен режим проверки:

```text
/admin -> Импорт CSV/XLSX -> Проверить без загрузки
```

После импорта бот показывает отчет:

- добавлено;
- обновлено;
- отключено;
- требует проверки;
- ошибки строк;
- найденные risk-tags.

Импорт не должен автоматически публиковать рискованные карточки.

Перед массовым импортом бот должен предложить экспорт текущей базы, чтобы можно было быстро откатиться к предыдущему состоянию.

#### Коллекции

Коллекции нужны, чтобы группировать наборы карточек:

- базовые задания;
- позы в стиле камасутры;
- сезонные/праздничные наборы;
- пользовательские наборы.

Карточка может входить в несколько коллекций.

#### Раздел «Экстрим»

Для чувствительных, но допустимых тем используется коллекция:

```text
restricted_content
```

Такие карточки не выпадают в обычной игре и в рулетке, пока админ не включит их для текущей сессии:

```text
/admin -> Экстрим: доступ закрыт -> ввод пароля
```

Повторное нажатие на `[Экстрим: доступ открыт]` выключает раздел без сброса остального
прогресса сессии. Сложные закрытые карточки дополнительно требуют level 4, hard opt-in и
указанный обязательный реквизит.

Пароль не хранится в коде и не коммитится. В `.env` хранится только SHA-256:

```text
ADMIN_CONTENT_PASSWORD_SHA256=
```

Запрещенные safety-теги из раздела 4.3 остаются запрещенными для импорта и не превращаются
в закрытый контент.

### 7.6. Позы в стиле камасутры

Позы добавляются как карточки `category = pose`, преимущественно в коллекцию `kamasutra_inspired_poses`.

Формат должен быть неграфичным:

- название;
- уровень;
- интенсивность;
- сложность;
- где удобно выполнять: кровать, пол, стул, стена;
- нагрузка на тело;
- реквизит;
- ограничения;
- медиа-схема или фото по желанию.

Не добавлять подробные графичные инструкции. Для карточки достаточно короткого описания положения, уровня близости, темпа и safety-заметок.

Отдельный план и стартовый список поз лежит в `docs/kamasutra-pose-pack.md`.

## 16. Дополнение v3: управление контентом и игровой поток

### 16.1. Редактируемая XLSX-книга

Экспорт из админки должен возвращать файл `карточки_и_реквизит.xlsx`, который без ручного
преобразования загружается обратно через `[Импорт XLSX]`.

Обязательные листы:

- `Флирт`, `Разогрев`, `Секс`, `BDSM`;
- отдельный лист `Экстрим`;
- `Реквизит`;
- `Справочники`.

В пользовательских ячейках используются русские названия и раскрывающиеся списки. Технические
коды оставляются только в колонках идентификаторов. Книга содержит подсказки для тем риска,
состояний и режимов реквизита. Импорт сначала выполняется в режиме проверки и сообщает число
карточек, реквизита и предупреждений. Неизвестный реквизит и некорректные уровни блокируют
соответствующую строку до исправления.

### 16.2. Режимы реквизита

У карточки задается один из режимов:

- `Не использовать`;
- `Можно добавить случайно`;
- `Обязателен`.

Явно указанный обязательный реквизит имеет приоритет. Если карточка предлагает игроку самому
выбрать предмет, бот не должен заранее подставлять конкретный предмет. Случайная подстановка
учитывает уровень, тип карточки, архивное состояние предмета и частоту в текущей сессии.

### 16.3. Уровни сессии по умолчанию

В настройках сессии можно включить или отключить каждый обычный уровень. Рулетка без ручного
выбора использует только включенные уровни. Настройка сохраняется при выходе в меню и позволяет,
например, оставить только `Секс` и `BDSM`.

### 16.4. Отдельный раздел «Экстрим»

`Экстрим` не является подпунктом обычного BDSM и появляется отдельной кнопкой только после
ввода админского пароля в текущей сессии. Для выдачи также нужны включенный BDSM/уровень 4 и
подтвержденная жесткая интенсивность. Запрещенные safety-теги нельзя открыть паролем.

### 16.5. Требования к текстам карточек

Игровой текст должен:

- прямо называть действие и роли игроков;
- задавать длительность или понятное условие завершения, если это нужно;
- отдельно указывать право остановки или замены карточки;
- не использовать внутренние ID, `light/medium/hard`, `check-in`, `aftercare` и другие
  непоясненные служебные термины;
- для интенсивных карточек завершаться понятной русской просьбой проверить самочувствие,
  предложить воду, отдых или другой заранее согласованный способ восстановления.

Заголовок формируется как `Раздел · Тип №N`. Номер считается внутри раздела и типа.

### 16.6. Сохранность административных правок

Стартовый импорт добавляет только отсутствующие встроенные карточки. Он не перезаписывает
текст, состояние и реквизит карточек, уже измененных администратором. Массовый ручной импорт
XLSX остается явной операцией обновления.

### 16.7. Критерии приемки v3

- экспортированная книга открывается, содержит все семь листов и импортируется без предупреждений;
- каталоги выводят по 10 записей и дают выполнить заявленные действия;
- `[Заменить карточку]` сразу выдает новую карточку тому же игроку;
- отключенные уровни не участвуют в общей рулетке;
- `Экстрим` отсутствует в клавиатуре до открытия доступа;
- активный таймер сообщает в Telegram `Время вышло`;
- выход в меню не завершает ход и не теряет активную карточку;
- повторный запуск приложения не отменяет правки, сделанные через админку;
- автоматические тесты, импорт-проверка, smoke-запуск и компиляция проходят без ошибок.
